## 1. 结论摘要

1. **前端侧无需再等后端**。当前站点的全部可见功能都落在「构建期静态」与「浏览器端计算」两层，实测零后端调用：`grep -rn "fetch(\|XMLHttpRequest\|axios\|/api/v1" frontend/src` 为空。已公开站点不依赖任何 Python 进程即可运行。
2. **FastAPI 不是「部署不上去」，而是运行模型不兼容**。Sites 只托管静态产物与平台自带的 Deno Function/Supabase，不运行 ASGI/Node 进程、不执行 middleware、没有文件系统持久化。`S11` 若把「Sites 上跑 FastAPI」当作验收目标，无论怎么改造都不会通过，必须先换定义。
3. **`S12` 的真实阻塞是数据许可，不是平台**。`backend/app/data/probe.py:67` 为 `"publishable": False`。只要公开展示/再分发条件未确认，路线 A/B/C 都拿不到「评委可看的真实价格」，换后端不解决这个问题。
4. **需要「服务端权威」的三件事在纯静态路线上不成立**：S13b 的跨设备持久化与重启恢复、S14 的后端唯一权威余额与服务端截断未来行情、S18 的用户实验记录持久化。它们的替代落点是 Supabase DB/Storage（个人 Free 不含，需套餐），或如实降级为「仅本浏览器会话、演示性质」。
5. **建议主路线为 A（静态 + 构建期预计算 + 客户端计算），C 作为可选增强，B 挂起**。A 完全落在 Sites 运行模型内、无费用与冷启动风险、满足「点开即可使用」；B 存在赛事合规疑问与运维风险，且在向官方确认前不应投入。

## 2. 落点分级

判定一段功能放在哪一层，只看一件事：**这段计算发生在谁的机器上**。

| 层 | 含义 | 谁执行 | 状态存放 | 是否需要额外套餐 |
| --- | --- | --- | --- | --- |
| L0 构建期静态 | 本地构建/脚本预先算好，产物是 HTML、JSON、索引文件 | 我们的本地机器（Qoder 会话） | 打进产物，只读 | 否 |
| L1 浏览器端计算 | 页面加载后在评委浏览器里算，含纯函数与交互状态 | 评委浏览器 | 内存/`sessionStorage`，仅本标签页 | 否 |
| L2 客户端调用外部 HTTPS API | 浏览器直接 fetch 第三方接口 | 远端第三方 | 第三方 | 否，但受 CORS/密钥限制 |
| L3 Sites Deno Edge Function | 平台托管的服务端函数，同源 `/functions/v1/...` | Sites 边缘 | 需自建存储，函数本身无状态 | 官方称 Functions 属服务端能力；本账户可用性**未验** |
| L4 Supabase 数据库 + Storage | 平台持久化服务 | Sites 服务端 | Postgres 表 / 平台对象存储 | **个人 Free 仅静态，不支持数据库与存储** |
| L5 Cloud Agents | 站点内嵌智能体能力 | 平台 | 平台 | 能力技能存在，**本会话未读取、未验** |

**Sites 明确不可承载**（来源：`deployment-validation.md` S04a 对官方 `environment.md`/`static-site.md` 的引用）：

- 任意 Python/ASGI 进程（含 FastAPI + uvicorn）；
- Next.js SSR、框架服务进程、middleware（本项目 `src/proxy.ts` 的 nextra/locales 代理在静态导出下不生效）；
- 文件系统持久化（SQLite 文件、上传目录、临时盘）；
- Notebook / Python 运行时（S20 的 statsmodels 训练不能在站点内发生）；
- 平台端口概念（本地 8000/7000/9000 只在开发用）。

## 6. 三条路线

### 路线 A：纯静态 + 构建期预计算 + 客户端计算（L0/L1）

- 覆盖：S10、S13a、S15–S18（预置形态）、S19、S20（本地）、S21、S22a/b。当前线上站点已是此形态。
- 优点：完全在 Sites 运行模型内；无费用、无冷启动、无跨域；评委点开即用；已具备 7 项线上证据。
- 硬限制：无服务端权威余额、无跨设备持久化、无按需新参数回测、数据体积受打包上限约束、外部密钥不可放前端。
- 风险：客户端可篡改（学习演示可接受，但文案不得称「服务端权威」）；「截断未来行情」要靠产物切分而非服务端保证。

### 路线 B：FastAPI 部署到独立 HTTPS 主机

- 覆盖：可实现 S13b/S14/S18 的服务端语义原样。
- 阻塞：
  1. 赛事要求「开发与部署均由 Qoder 完成」，第三方主机部署是否合规**未确认**，需向官方提问，不自行推断；
  2. 与「后续所有功能都建立在 Sites 基础上」的用户约束相冲突；
  3. 需精确 origin 的 CORS（`config.py:16` 现仅 localhost）、HTTPS 证书、费用、进程守护与评审时段可用性；休眠/重启未验；
  4. 站点→外部 API 的浏览器实测从未执行。
- 建议：**挂起**，仅在官方明确认可且愿意承担运维时启用。

### 路线 C：Sites Deno Edge Function + Supabase（L3/L4）

- 覆盖：可成立 S13b、S14 访客隔离与服务端截断、S18 用户实验持久化，且仍在 Sites 平台内，符合用户长期约束。
- 前置与未知：个人 Free 不支持数据库/存储，需升级套餐（本账户套餐与额度未核对）；Function 的 CPU/时长/包体限制未验；现有 FastAPI 逻辑需按 Deno 重写，SQLite 事务语义换成 Postgres；`/functions`、`/rest/v1`、`/storage` 为保留命名空间，自有路由须避让。
- 建议：作为**可选增强**，且在实现前先做第 7 节的 F1/F2 最小验证；不与路线 A 争夺主线，A 先交付闭环。

### 推荐顺序

A 先把「真实数据→因子→候选→回测→训练→实验记录」的**可复现闭环**在静态产物上做完整；同时向官方确认 B 的合规性；只有当作品确实需要「用户自建实验跨设备保存」或「服务端权威账户」时，才按 C 升级并先完成 Function/Supabase 实测。任何路线选择都不改变 S12 的数据许可前置。

## 7. 未验清单与最小验证方法

| 编号 | 待验项 | 为什么关键 | 最小验证动作（不换域名、不购买，除 F2 需要授权） | 判定标准 |
| --- | --- | --- | --- | --- |
| F1 | Function 可用性与资源上限 | 决定 C 是否可行 | 在现有站点 prepare 一个最小 `functions/v1/app` 回显 JSON，同源浏览器 fetch | 返回 200 + JSON；记录实际超时/包体/是否需套餐 |
| F2 | 本账户是否可用数据库与 Storage | 决定 S13b/S18 升级成本 | 只读 `get_database_schema`/`list_storage_objects`，不创建、不购买 | 能读到结构=可用；权限/套餐报错=需升级，据实记录 |
| F3 | 站点→外部 HTTPS API 浏览器请求 | 决定 L2 是否可用 | 同源页对一个可控 HTTPS 端点发起 fetch | CORS 精确 origin 通过才记「可用」 |

## 8. 决策门槛

出现下列任一需求，纯静态路线 A 就不够，必须显式升级到 C 或经官方认可后使用 B，并在计划里重开对应任务：

1. 需要**服务端权威余额/防篡改**账本（当前客户端计算不能满足，改文案也不等于满足）；
2. 需要**用户自建实验记录跨设备/重开浏览器后仍在**；
3. 需要**全 A 股日频数据**或按需区间查询（体积与许可都不允许打包）；
4. 需要**按需实时行情**或调用带密钥的第三方 API（密钥不可置于前端，必须由函数代持）；
5. 需要**评委现场改参数即时回测**（构建期预计算只覆盖固定参数）。

反之，若以上都不是作品的必要卖点，则不引入 L3/L4，以保持「点开即用」和零运维为优先。
